# Telegram setup: SkillForge on the GB10

Step-by-step for the operator on the GB10. Telegram uses **long-polling**, so the GB10 needs no inbound port, tunnel or webhook,
only outbound HTTPS to `api.telegram.org`.

Status labels: **VERIFIED** = checked on this GB10 · **FROM DOCS** = NemoClaw/Telegram or repo docs, not run here ·
**INFERRED** = our reading, unconfirmed.

| File | Purpose |

| `telegram.env.example` | Variable names only (no values) |
| `telegram-egress.yaml` | Fallback egress rule (`api.telegram.org:443` only); the built-in preset supersedes it |

## Ground rules
1. **Secrets live only in `~/.config/skillforge/`** (dir 700, files 600). Never in the repo, shell history, chat or a screenshot.
2. **Approvals never happen over Telegram.** Promoting a skill or executing an action needs a named person at the host CLI.
   Replying "approved" to the bot grants nothing. VERIFIED offline: the agent has no approve tool and `--by agent` is rejected.
3. **One poller per bot token.** A second process with the same token gets `409 Conflict`.
4. **DM-only and allowlisted.** `TELEGRAM_GROUP_POLICY=disabled`, `TELEGRAM_REQUIRE_MENTION=1`, and only the ids in
   `telegram_allowed_ids` are answered.

## Step 1: Create the bot (Telegram app)
1. **@BotFather** -> `/newbot` -> a display name and a username ending in `bot`. Copy the **bot token**; treat it like a password.
2. **@userinfobot** -> `/start` -> note your **numeric user id**.

## Step 2: Store the token and allowed ids on the GB10
`read -rs` keeps the token off the screen and out of shell history.
```bash
umask 077
install -d -m 700 ~/.config/skillforge
read -rs -p "Bot token: " T; echo; printf '%s\n' "$T" > ~/.config/skillforge/telegram_token; unset T
read -r  -p "Allowed numeric user id(s), comma separated: " I; printf '%s\n' "$I" > ~/.config/skillforge/telegram_allowed_ids; unset I
chmod 600 ~/.config/skillforge/telegram_token ~/.config/skillforge/telegram_allowed_ids
stat -c '%a %n' ~/.config/skillforge/telegram_*     # expect 600 for both
```
Always set the allowed ids; without them NemoClaw falls back to device pairing (FROM DOCS).

## Step 3: Pre-flight check (no API calls)
```bash
sg docker -c "bash integrations/telegram/telegram-setup.sh --check"
```
Every line should be `[ok]`, then exit 0 (permissions, both files, `nemoclaw` on PATH, DNS).

## Step 4: Connect the Telegram channel
> **Preferred (how the live sandbox was built):** configure Telegram at sandbox creation. Export the `TELEGRAM_*` variables and the
> provider env (`NEMOCLAW_NON_INTERACTIVE=1 NEMOCLAW_COMPATIBLE_AUTH_MODE=none NEMOCLAW_PROVIDER=custom
> NEMOCLAW_ENDPOINT_URL=http://127.0.0.1:8000/v1 NEMOCLAW_MODEL=skillforge-qwen`), then
> `nemoclaw onboard --name skillforge --non-interactive`. No rebuild is needed. A later `channels add` rebuilds the sandbox, and
> without `NEMOCLAW_COMPATIBLE_AUTH_MODE=none` that rebuild deleted the old sandbox and failed at provider selection
> (seen 2026-10-25; `telegram-setup.sh` now exports the provider env).

```bash
sg docker -c "bash integrations/telegram/telegram-setup.sh"          # default sandbox: skillforge
```
The script (FROM DOCS): exports the secrets from the files without echoing them and sets DM-only mode; runs
`nemoclaw <sandbox> channels add telegram` unless the channel exists (this rebuilds the sandbox); applies the `telegram` egress
preset after a dry run; unsets the secrets and prints the next steps.

## Step 5: Verify
| # | Check | Expected |
|---|---|---|
| 1 | `nemoclaw skillforge policy list` | `telegram` preset listed |
| 2 | DM the bot "hello" from the allowed account | a reply generated by the local Qwen (`skillforge-qwen`) |
| 3 | `nemoclaw skillforge logs --follow --since 5m` while you DM | inbound message and reply logged, no errors |
| 4 | DM from a **non-allowlisted** account | no answer, or a denial |
| 5 | `openshell term` during 2-4 | egress only to `api.telegram.org:443` and `inference.local`; anything else is a finding |

Checks 1-3 passed on 2026-10-25 (OCSF: getUpdates -> inference.local -> sendChatAction -> sendMessage, all ALLOWED by
`telegram_bot`; Qwen served the replies; OpenClaw's own telemetry to `telemetry.openclaw.ai` was DENIED by the restricted tier).
Checks 4-5 are not done. That is a **Telegram <-> local model round trip**, not a Telegram <-> SkillForge workflow.

## Step 6: let Telegram call SkillForge tools
The two halves are each verified on the GB10 (Telegram <-> local model above; OpenClaw in the sandbox -> SkillForge host tools, Gate 2, records-ops tools, [CLAIMS.md](../../docs/CLAIMS.md) #23c). The joined chain is not recorded. Path (INFERRED):
```
Telegram -> NemoClaw/OpenClaw bridge (allowlist) -> OpenClaw agent + SkillForge skill
        -> client.py <tool> '<json>' -> POST /call -> SkillForge tool service (python -m app serve, bridge-bound)
        -> result -> agent -> Telegram reply           (approval: host CLI only)
```
Needs the tool service bound to the openshell bridge gateway (never `0.0.0.0`; refused by design, VERIFIED; done for Gate 2 with `--bind 172.18.0.1`), the
`adapters/openclaw/presets/host-tools.yaml` policy applied after a dry run (done for Gate 2), and the skill packaged into the sandbox. Limits are in
`GAPS.md`.

## Step 7: Troubleshooting
| Symptom | Fix |
|---|---|
| `409 Conflict` | another process polls this token: stop it, or `/revoke` and use a new token |
| no reply | check the allowlist id; `logs --follow`; `nemoclaw skillforge recover`, then `rebuild --yes` |
| reply without model output | `curl -s 127.0.0.1:8000/v1/models` on the host |
| egress blocked | `policy list`; re-apply `policy add telegram --yes` |

## Step 8: Roll back
```bash
nemoclaw skillforge channels remove telegram
shred -u ~/.config/skillforge/telegram_token ~/.config/skillforge/telegram_allowed_ids
```
Then `/revoke` (or `/deletebot`) in @BotFather.
